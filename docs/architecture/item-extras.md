# Item extras: history, icons, breaches, usage, health, bulk changes

Client features behind the item list and item detail screens of the apps
(created date, "Eintragsverlauf", website icons, "Kompromittierte
Passwörter", "Zuletzt verwendet" / "Letztes Auto-Ausfüllen", the per-item
"Sicherheits-Check" and multi-select). They exist in the Rust client
(`crates/client`, used by the CLI, desktop and through `crates/ffi` by iOS
and Android) and in the TypeScript client (`packages/client`, web and
extension). All FFI calls are blocking: run them on a background task
(Swift `Task.detached`, Kotlin `Dispatchers.IO`).

## Created date

The server sends `createdAt` (Unix ms) with every item in `/api/v1/sync`.
Clients expose it as `Item.created_at` (Rust), `Item.createdAt` (FFI, TS).
It is 0 (TS: 0 or absent) from servers that do not send it yet.

## Item history ("Eintragsverlauf")

Every update of an item keeps the replaced encrypted version on the server
(table `item_versions`, newest 20 per item, removed when the item is deleted
permanently or its vault is deleted). Re-encryptions after a key rotation are
versions too. The server cannot read them: each version stays bound to its
own revision and key epoch through the item's associated data
(`passbox/v1/item|vault|item|revision` or `passbox/v2/item|…|epoch`), so it
cannot pass off an old version as the current one either.

| | Call | Returns |
| --- | --- | --- |
| HTTP | `GET /api/v1/items/{id}/versions` | `{ versions: [{ revision, keyEpoch, encryptedData, updatedAt, updatedBy }] }`, newest first |
| Rust | `client.item_history(id)` | `Vec<ItemVersion { revision, updated_at, updated_by, data: Option<ItemData> }>` |
| FFI | `itemHistory(id)` | `[ItemVersion { revision, updatedAt, updatedBy?, data? }]` |
| TS | `client.itemHistory(id)` | `Promise<{ revision, updatedAt, updatedBy, data: ItemData \| null }[]>` |

`data` is empty when this device cannot decrypt the version, typically a
shared vault's version from before a key rotation that the account was not a
member for (it never received that epoch's key). Show such entries as
"Diese Version kann auf diesem Gerät nicht angezeigt werden" instead of
hiding them. `updatedBy` is the public session ID of the device that saved
the version; match it against `sessions()` to show a device name.

**Restoring** a version is a normal update with its data:
`updateItem(id, version.data)`. That saves it as a new version (so the restore
can be undone from the history too) and keeps the password history.

## Website icons

Apps never contact the websites in a vault. An icon is looked up in these
tiers, first match wins:

| Tier | Where | Who learns the domain |
| --- | --- | --- |
| Bundled | `packages/site-icons` in the app: 3,516 popular sites (32 px), the top 1,000 also at 64 px; iOS and Android the top 1,000 at 64 px | nobody: no request, and the server is never asked for a bundled site |
| Device cache | Rust client: store, 7 days ("no icon" a day); TS client: memory; extension: session storage | nobody |
| Server memory | the server process, 6 hours (misses 1 hour) | the server |
| Server database | `site_icons` (migration 0003), shared by all users and server processes | the server |
| Fetch | the website, over HTTPS with strict protection against server-side request forgery, then stored for everyone | the server; the website sees the server's address, once per site |

`GET /api/v1/icons/{domain}` (session required) answers from the server's
tiers. The store is not tenant data: a row says which icon a website has,
never who asked. It has forced row level security anyway (every context
reads, only the `icons` request context and the `worker:icons` refresh job
write, see [database-security.md](database-security.md)), the lookup runs
in the `icons` context rather than as the account, and request logs show
`/api/v1/icons/{domain}` instead of the domain, so no log line ties a site
to a session or account. A background job (`api::icons::spawn_refresher`,
every 10 minutes, rows claimed with `FOR UPDATE SKIP LOCKED`) checks icons
again after 30 days with `If-None-Match`/`If-Modified-Since` and misses after
7 days; an icon that fails three times a day apart becomes a miss; entries
nobody asked for in 180 days are removed. `/metrics` counts lookups by tier
and refreshes by outcome. See [self-hosting.md](../self-hosting.md#website-icons)
for the fetch rules, storage and the privacy note. Admins can turn the
server tiers off (`PASSBOX_ICONS=off`, `/api/v1/meta` → `icons: false`);
the server then answers 404 and other sites show monograms. Bundled icons
need no server and still show in the extension and the mobile apps; the web
app and desktop app hide all icons when `meta.icons` is false. The user's
"Website-Icons anzeigen" turns all of them off.

**Bundled icons** (`packages/site-icons`): generated by
`node scripts/update-site-icons.mjs` from the top domains of the Majestic
Million (CC BY 3.0; source, date and license in
[THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md)), fetched with the
server's own fetcher (`cargo run -p passbox-server --example fetch-site-icons`,
same rules) and scaled in headless Chromium. Domains match exactly or with
`www.` removed; other subdomains are different sites.

| Pack | Format | Size | Used by |
| --- | --- | --- | --- |
| `packs/web-32.pbia` | atlas: one WebP with 3,516 tiles of 32 px and a domain index | 1.6 MB | web, desktop, extension |
| `packs/web-64.pbia` | atlas, 1,000 tiles of 64 px | 1.1 MB | the same, on screens with more than one pixel per point (and in the extension's service worker) |
| `mobile/site-icons-64.pbic` | one WebP per site (64 px), with an index | 1.7 MB | iOS app (resource, the AutoFill extension reads the app's copy), Android app (asset) |

The web packs (2.7 MB together, a test keeps them under 3 MB) are assets
that load on the first icon, not part of the JavaScript bundle; one atlas
compresses to less than half of one file per icon. The mobile pack adds
about 1.7 MB to each app; it stays at 1,000 sites because one file per icon
needs no image decoding in the Rust client. Formats: `src/pack.ts` (atlas)
and `crates/client/src/site_icons.rs` (single images).

| | Call | Returns |
| --- | --- | --- |
| Rust | `client.icon(domain)` | `Option<Vec<u8>>` (PNG, ICO, JPEG, GIF or WebP) |
| Rust | `site_icons::set_bundled_site_icons(Some(SiteIconPack::parse(bytes)?))` | installs the bundled pack for the process |
| FFI | `icon(domain)` | `Data?` / `ByteArray?` |
| FFI | `setBundledSiteIcons(pack)` | number of sites; iOS `BundledSiteIcons.installFromBundle()`, Android `BundledSiteIcons` (both lazily before the first icon) |
| TS | `client.iconUrl(domain)` | `Promise<string \| null>` (`data:` URL for `<img>`; the CSP allows `data:` images); bundled first |
| TS | `bundledSiteIcon(host)`, `isBundledSite(host)` from `@passbox/site-icons` | the bundled tiers alone |
| TS | `api.icon(domain)`, `iconPath(domain)` | raw bytes and content type |

Pass the bare host name (`github.com`; punycode for international names in the
Rust client). The Rust client caches results in its store for 7 days ("no
icon" for a day) under keys `cache_icon_<domain with _ for .>`, and returns a
cached icon when offline. Apps keep store keys starting with `cache` in
files, not in the keychain (iOS `AppSecureStore` does this).

**User preference:** apps offer "Website-Icons anzeigen" (default on) and
show a monogram when it is off, when `meta.icons` is false or when there is
no icon. The preference is local to the app.

**Where they show:** logins with a public host name (not IP addresses or
names without a dot) show their icon on a light rounded tile
(`SiteIcon` in `packages/ui`), with the tinted monogram while it loads and
when there is none; other categories keep their category icon.

| App | Places | Setting and cache |
| --- | --- | --- |
| Web, desktop | item list, item detail header, command palette, security check lists, trash, archive, emergency access, share dialogs (`ItemIcon`) | Settings → "Sprache und Darstellung" (`passbox.preferences` → `showWebsiteIcons`); icons load when a row scrolls into view, six at a time, and stay in the client's memory until it is reloaded |
| Extension | popup list, item view and trash, inline menu, save banner (`WebsiteIcon`) | Settings → "Darstellung" (`showWebsiteIcons` in `chrome.storage.local`); the service worker loads them (`popup.icon`, `frame.icon`) and keeps them in `chrome.storage.session` (memory only) until the vault locks |
| iOS, Android | lists and detail | in the app's settings; Rust client cache (above) |

The extension does not use the browser's own favicon cache (the `favicon`
permission and `_favicon/` URLs): that needs another permission, exists only
in Chromium and knows only sites the browser has visited. The save banner
shows no icon for a site that looks like another one (G17), so a phishing
page does not look more trustworthy.

## Brand icons of third-party services

Icons of the services Passbox names in its own UI (import sources, alias
providers, identity providers, SIEMs, browsers and app stores, agent clients,
Have I Been Pwned, 2fa.directory, AI providers) are a different thing: they
are bundled with the apps in `packages/brand-icons` (64 px PNGs, a manifest
with the source URL and date of each, see
[THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md)) and never loaded at
run time. `brandIcon(domainOrId)` returns the bundled URL (by ID such as
`okta`, host name such as `okta.com` or `acme.okta.com`, or URL);
`<BrandIcon service="okta" />` from `@passbox/ui/brand-icon` draws it on the
same tile as website icons, with the service's name as alternative text
(`decorative` when the name is written next to it). Refresh the set with
`node scripts/update-brand-icons.mjs [id …]`; add services in
`packages/brand-icons/services.json`.

## Breach check ("Kompromittierte Passwörter")

Have I Been Pwned's range API with k-anonymity: only the first 5 hex
characters of the password's SHA-1 hash are sent, with `Add-Padding: true`;
matching happens on the device (`passbox_core::breach`).

| | Call | Returns |
| --- | --- | --- |
| Rust | `client.breach_check(password)` | `u64` (0 = not found) |
| Rust | `client.check_breached_items()` | `Vec<BreachedItem { item_id, count }>`, most breached first |
| FFI | `breachCheck(password)`, `breachedItems()` | `UInt64`, `[BreachedItem { itemId, count }]` |
| TS | `breachCount(password)`, `client.checkBreachedItems()` | `Promise<number>`, `Promise<{ itemId, count }[]>` |

By default the range requests go through the user's Passbox server
(`GET /api/v1/breach/range/{prefix}`), so Have I Been Pwned never sees the
device's IP address; `set_breach_mode` / `breachMode` choose `auto`,
`server` or `direct`. The vault-wide security analysis (score, findings,
"fix these first", dismissals, email monitoring) is described in
[security-analysis.md](security-analysis.md).

`check_breached_items` covers logins outside the trash, sends one request per
hash prefix and keeps the results in memory until the vault locks. It is slow
for large vaults: run it in the background. Offline it fails with
`Network` ("Have I Been Pwned could not be reached"). The check is opt-in:
ask once and explain what is sent ("Nur die ersten 5 Zeichen eines
Prüfwerts Ihres Passworts werden an Have I Been Pwned gesendet – nie das
Passwort selbst.").

## Usage ("Zuletzt verwendet", "Letztes Auto-Ausfüllen")

A device-local map item ID → `{ lastUsedAt, lastAutofilledAt, useCount }`,
encrypted with the account key (`Keyring::encrypt_local`, purpose
`item-usage`) and never sent to the server. Times are Unix ms, 0 = never.

| | Call |
| --- | --- |
| Rust | `client.record_item_use(id, UsageKind::Copy \| Autofill \| Open)`, `item_usage(id)`, `item_usages()` |
| FFI | `recordItemUse(id, kind: .copy/.autofill/.open)`, `itemUsage(id)`, `itemUsages()` (map by item ID) |
| TS | `client.recordItemUse(id, "copy" \| "autofill" \| "open")`, `itemUsage(id)`, `itemUsages()` |

Every kind sets `lastUsedAt` and counts a use; `autofill` also sets
`lastAutofilledAt`. Call it when a field is copied, when the item is opened
and from the iOS AutoFill extension / Android Autofill service after filling.
The Rust client stores it under the store key `cache_usage`, the TS client in
`localStorage` (`passbox.usage.<accountId>`). Signing out deletes it.

## Per-item health ("Sicherheits-Check")

The same rules as the vault health (`health()`), for one item:

| | Call | Returns |
| --- | --- | --- |
| Rust | `client.item_health(id)` | `ItemHealth { problems: Vec<ItemProblem>, strength: Option<u8>, reused_with, breach_count: Option<u64> }` |
| FFI | `itemHealth(id)` | `ItemHealth { problems: [ItemProblem], strength?, reusedWith, breachCount? }` |
| TS | `client.itemHealth(id)` | `{ problems: ItemProblem[], strength, reusedWith, breachCount }` |

Problems, in this order: `weak` (score ≤ 1), `reused`, `insecure_url`
(`http://`), `missing_totp` (a login with a password but no one-time
password), `breached` (only known after a breach check in this session;
`breachCount` is `null`/`None` before). FFI enum cases: `.weak`, `.reused`,
`.insecureUrl`, `.missingTotp`, `.breached` (Kotlin `WEAK`, `REUSED`,
`INSECURE_URL`, `MISSING_TOTP`, `BREACHED`). Items in the trash and other
categories have no problems.

## Bulk changes (multi-select)

| | Call | Returns |
| --- | --- | --- |
| Rust | `client.trash_items(&ids)`, `client.set_favorite(&ids, favorite)` | `Vec<BulkFailure { item_id, error }>` |
| FFI | `trashItems(ids)`, `setFavorite(ids, favorite)` | `[BulkFailure { itemId, error }]` |
| TS | `client.trashItems(ids)`, `client.setFavorite(ids, favorite)` | `Promise<{ itemId, error }[]>` |

Items are written one after another with a single sync at the end; items
that already have the requested state are skipped. Failures (for example an
item changed on another device meanwhile) are reported per item and do not
stop the others. Losing the connection or the session stops the operation
with `Offline` / `Locked`. Trashed items can be restored for 30 days, so an
undo toast is enough confirmation.
